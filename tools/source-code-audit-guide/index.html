修改已有源码，最危险的不是“不会写代码”，而是不知道哪些逻辑绝对不能碰。

一个看似简单的“加提醒”可能触发状态重复；一个“改止损”可能同时改变手数、回测和统计。源码修改必须先建立结构图，再冻结范围。

修改前先回答八个问题

01

这是EA、指标还是策略脚本？

执行型代码和显示型代码的风险完全不同。先识别OnTick/OnCalculate/strategy()/indicator()等入口。

02

谁负责Entry？

找到真正决定开仓/信号的函数、条件组合和状态变量，而不是只搜“Buy/Sell”。

03

Exit与Risk在哪里？

止损、止盈、手数、ATR、固定风险可能分散在多个模块中。

04

有没有状态机？

Probe、Wait、Armed、Filled、T1、Protected、Closed等状态决定同一条件能否重复执行。

05

是否多周期？

request.security、CopyRates、iTime等调用会引入周期同步、重绘和性能问题。

06

是否写文件或发提醒？

CSV、SendMail、SendNotification、Alert、Webhook都可能改变执行频率或权限要求。

07

有没有外部依赖？

iCustom、DLL、WebRequest、外部指标、授权服务器都必须先确认。

08

本次明确不改什么？

必须把“保持不变”的Entry/SL/T1/T2/统计逻辑单独列出来。

推荐修改流程

Local Inspection

先用浏览器本地体检识别平台、函数、下单、管理、多周期、提醒、文件和潜在敏感信息，不上传源码。

Deep Analysis

需要真正重建逻辑时，再进入AI深度分析，输出当前逻辑摘要、Entry/Exit/Risk/State和冲突。

Freeze Scope

把本次修改、必须保持不变和待确认问题冻结。范围没冻结，不生成修改版。

Generate + Changelog

输出完整源码，而不是零散补丁；同时记录Changed / Unchanged / Warning。

Compile + Scenario Audit

编译通过后，用关键历史案例验证状态和输出，而不是只看“无报错”。

哪些修改属于高风险

修改风险原因
Entry / Exit直接改变交易样本和统计分布
状态变量 / reset逻辑可能制造重复信号、重复订单或永久锁死
手数 / 风险计算同一SL下账户风险会改变
多周期数据容易产生同步、重绘或历史/实时差异
平台转换Pine、MT4、MT5的事件模型和订单模型不同，不能逐行翻译
提醒 / Webhook若挂在观察事件而非正式Entry上，会造成大量误报
